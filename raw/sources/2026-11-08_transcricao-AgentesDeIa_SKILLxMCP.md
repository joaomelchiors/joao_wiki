# SILL vs MCP

Pessoal, antes de a gente fazer o nosso primeiro MCP de forma prática, eu gostaria de gravar uma aula para explicar a diferença que existe entre skills (habilidades) e MCPs, tá? Uma coisa que eu queria ressaltar nesta aula é que, no caso específico dos MCPs, sempre vai haver código por baixo. Você não precisa conhecer esse código nem saber como o MCP funciona internamente, mas saiba que todo MCP demanda uma implementação em código, porque, no final das contas, ele é um conector da IA com os sistemas. Então ele precisa de código.

As skills nem sempre precisam de código. Uma skill é uma habilidade, é como se fosse uma receita, um manual para fazer uma determinada atividade. Ela pode executar essa atividade simplesmente utilizando trechos de prompt e acessando a IA, como também pode ter codificação. É possível implementar dentro de uma skill coisas que funcionariam num MCP. Não existe uma barreira específica. O que a gente está colocando aqui como diferença entre skills e MCPs é mais a ideia do propósito. Cada ferramenta tem a sua razão de ser, e eu queria compará-las para você entender que são duas ferramentas complementares.

Vamos lá. A skill vai ensinar o agente de IA a fazer alguma coisa: como implementar uma determinada página de um dashboard que você está criando, como nós fizemos com aquele gráfico de pizza; como pegar uma fatura e transformá-la em um arquivo com uma lista categorizada; como pegar uma determinada lista, gerar um sumário, fazer as contas e chegar a um resultado final. Ou seja, a skill ensina como fazer algo, como se fosse um manual com todos os passos necessários.

Por exemplo, responder cliente. A skill vai ler a mensagem, pode ter uma série de lógicas internas para identificar problemas comuns e, no final, vai responder o cliente no tom certo, de acordo com o que a empresa entende ser a melhor forma de tratar os clientes, tá? Então ela define um passo a passo, traz as regras e boas práticas, e pode usar apenas o modelo, como também pode chamar algumas ferramentas ou usar linguagem de programação.

“Léo, a gente está usando aquela ideia de desenvolvimento baseado em especificação, em que temos os passos, certo? É possível também colocar esse passo a passo dentro de uma skill?” Sim, você pode usar aquela estratégia de ter passo 1, passo 2, passo 3, passo 4, ou mais passos, caso queira, dentro de uma habilidade. E qual é a vantagem de colocar esse passo a passo numa skill? É que você pode transformar a skill em um comando, como, por exemplo, responder-cliente. Quando você chama o responder-cliente, automaticamente ele já tem todo o processo de como responder o cliente. Ou seja, você pode ter um passo a passo, trazer as regras e boas práticas, acessar o modelo quantas vezes quiser e até usar linguagem de programação dentro de uma skill. Você tem um manual de como fazer alguma coisa, e dentro desse manual pode usar diversas ferramentas.

Já o MCP vai te dar acesso às ferramentas que você vai usar numa determinada ação. O MCP funciona como um plugue. A gente já fez essa analogia, né? Você tem o agente de IA, e o agente tem esse plugue, esse conector, que permite que ele acesse o Gmail, o Google Drive, a agenda, o calendário, um banco de dados, os sistemas da sua aplicação e assim por diante, tá? Ou seja, ele conecta a IA a sistemas externos.

Eu poderia fazer essa conexão com sistemas externos dentro de uma skill? Pode, não tem problema. Nada vai te impedir de fazer isso. Mas o MCP é mais voltado para essa necessidade. Com ele, você pode expor algumas ferramentas ou dados específicos de um sistema, tá? E ele padroniza a forma de integrar a IA com uma ferramenta, por exemplo, um sistema externo. Além disso, ele permite que você execute ações nesses sistemas que vão além do chat.

E, no final, o agente usa os dois: as skills e os MCPs. Eu coloquei aqui um exemplo e quis dar um zoom, porque o MCP tem muito essa característica de conectar com um sistema e definir ações. Não se preocupe muito com os detalhes desta parte, tá? Isso é irrelevante no nosso caso. Mas você tem ações. Por exemplo: eu tenho um conector do Gmail. Ele vai ter uma ação para marcar o e-mail como lido, outra para arquivar o e-mail, excluir o e-mail, ler o e-mail, responder o e-mail, enviar o e-mail e assim por diante. Então você tem várias ações dentro de um conector, cada uma para uma tarefa específica. Se você está conectando com o Google Drive, ele vai ter outras ações, como ler o conteúdo de uma pasta, criar um arquivo ou mover um arquivo de uma pasta para outra.

Ou seja, além de estabelecer uma conexão com uma aplicação, o MCP tem ações. Na hora de criar um MCP, você vai definir as ações que ele suporta. E, uma vez que você tem essas ações, o seu agente de IA consegue usá-las para fazer coisas concretas dentro do sistema: criar um arquivo, excluir uma pasta, mover um arquivo de um lugar para outro, ler um e-mail, marcar um e-mail como spam, desmarcar um e-mail como spam. São ações reais, que integram o seu agente de IA com o sistema. Então esse aspecto de ter essas ações atreladas ao conector, a esse MCP aí, é importante.

Então, imagine que a skill vai ter uma habilidade, vai ensinar um passo a passo para fazer algo. O MCP não tem esse passo a passo, o MCP não é um “como fazer”. O MCP vai te dar as ferramentas para que você possa fazer isso em outro momento, usando a skill ou uma especificação. Essa é a diferença. A skill já traz o passo a passo. O MCP te dá ferramentas e ações para integrar, por exemplo, com algum outro sistema.

Então a gente pode fazer esta comparação: a skill responde à pergunta “como executar?”. Já o MCP responde à pergunta “qual ferramenta usar?”. Ele te dá uma listinha de ferramentas, e a partir daí você consegue acessá-las. A skill tem a função de orientar a IA, definir como fazer algo em determinada situação ou direcionar a IA para um tipo de ação específica. Já o MCP tem o propósito de integrar com sistemas, tá? Numa analogia, a skill seria um manual, uma receita para fazer alguma coisa, e o MCP seria uma tomada, um conector com um sistema externo que te dá uma série de funcionalidades.

Resumindo: a skill ensina o processo, e o MCP dá acesso às ferramentas necessárias para que esse processo possa ser executado. São duas coisas distintas. Um é um conector que te dá uma série de funcionalidades. A outra ensina uma habilidade ou faz uma coisa específica.

“Léo, então qual é a diferença entre uma skill (habilidade) e uma especificação, que é o que a gente está trabalhando?” A diferença é que a skill é focada. Ela tem um foco específico em uma coisa só. Então uma skill vai ser responsável por responder o cliente. Outra skill vai ser responsável por classificar o tipo de pergunta que o cliente fez. Outra vai verificar se a resposta tem o tom correto. E outra vai verificar se a pergunta está fora do escopo e cuidar da resposta quando o assunto não está definido na base de dados da empresa. Ou seja, a skill foca num ponto específico.

Já no desenvolvimento orientado por especificação, você desenvolve qualquer funcionalidade ou fluxo dirigido por uma especificação. A especificação cuida do processo como um todo, de ponta a ponta, e cada passo pode indicar como deve ser executado através de uma skill, como nós fizemos agora há pouco. E aí o MCP entra como esse terceiro pilar, que te dá as ferramentas para executar trabalho de verdade, integrando ferramentas de mercado ou mesmo as ferramentas usadas dentro da empresa, no seu dia a dia. Você pode integrar os seus agentes com as ferramentas de software concretas que você usa para fazer trabalho real.

Então esses três pilares são importantes: o desenvolvimento baseado em especificação cuida do fluxo, a skill cuida de como fazer determinadas coisas específicas e focadas, e o MCP cuida do acesso às ferramentas externas. Com esses três, a gente pode fazer muita, muita coisa incrível, e é isso que vamos continuar vendo neste capítulo de MCP, para, no próximo, começarmos os nossos projetos.
